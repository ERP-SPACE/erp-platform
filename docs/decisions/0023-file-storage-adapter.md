# 0023 — File storage behind an adapter; local filesystem for development

- **Status:** Accepted
- **Date:** 2026-10-24
- **Needs confirmation from:** nobody

## Context

Stage 1 needs file uploads: salesman KYC documents (PAN, Aadhaar, agreements). Later stages add PDFs, labels and import files. ADR-0019 planned MinIO as the local S3 stand-in, but its public image was withdrawn. Docker Compose now keeps MinIO behind an opt-in profile. Production (Stage 7) uses S3.

## Decision

- `StorageService` in `apps/api/src/storage` is the only code that touches stored files. Its interface is `put(prefix, bytes, ext) → key`, `open(key)` and `remove(key)`.
- **Development and test:** a local filesystem adapter under `STORAGE_DIR` (default `erp/.storage/`, gitignored).
- **Stage 7:** an S3 adapter with the same interface, chosen by `STORAGE_DRIVER=s3`.
- **Keys** are generated by the service as `{prefix}/{uuidv7}.{ext}`. They are never built from user-supplied file names. The original name is kept only as metadata in the database. Paths are checked so they can't escape the root.
- **Uploads** are limited by `UPLOAD_MAX_BYTES` (default 5 MB). Only PDF, PNG and JPEG are accepted, checked by magic bytes rather than by the declared type or the extension.
- **Downloads** go through an authenticated, permission-checked API route. They are served with `Content-Disposition: attachment` and `X-Content-Type-Options: nosniff`.

## Consequences

- No S3-compatible container is needed for local development.
- The same API code moves to S3 unchanged.
- Local files are not backed up. Back up `.storage/` together with the database dump if local data matters.
