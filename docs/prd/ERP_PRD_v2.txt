
Product Requirements Document
Paper Trading ERP System
Sublimation & Speciality Paper  |  Phase 1  |  Surat Hub
Version 2.0


Executive Summary
This ERP manages end-to-end operations of a sublimation and speciality paper trading business. It integrates purchase workflows, landed cost allocations, roll-level inventory management, barcode-based traceability, customer onboarding, credit management, salesman/broker commission tracking, and a foundational accounting layer.
The ERP replaces fragmented spreadsheets and external accounting tools (such as Tally) with a unified, scalable platform. Phase 1 focuses on Gujarat (Surat hub) with architecture designed for pan-India rollout.

WhatsApp Automation — Deferred to Phase 2
WhatsApp-driven ordering, dunning, ledger queries, and broadcast automation are intentionally deferred to Phase 2.
Phase 1 captures all required data fields (WhatsApp number, language preference, consent flag) so that Phase 2 integration requires no structural schema changes.
 | 
Accounting — Phase 1 Scope (Foundational Only)
Phase 1 implements auto-voucher generation from every PI and SI, a full chart of accounts, GST-ready ledger structure, basic AR/AP aging views, and a monthly GST summary export.
Full financial statements, bank reconciliation, GSTR API filing, year-end close, and TCS computation are Phase 2 items.
 |

6. Core Modules & Workflows
6.1 Product Catalogue & Barcoding
Hierarchy: GSM → Quality → Size (Width).
Lengths: Default 1000 m; configurable to 1500/2000 or custom odd number (admin approval).
Barcodes: Unique QR + alphanumeric serial generated automatically on GRN posting.
Each roll mapped to vendor and batch on inward.
Reprint option for damaged labels or returned rolls.

Barcode Format
Format:   YYMM-SUP-BATCH-ROLLID-CHECK
QR Payload: { roll_id, sku_id, batch_id, vendor_id, length_m, width_in, landed_cost }
 | 
6.2 Purchases & Inwarding
Workflow
Create PO (Draft → Approved). Supports multiple invoices per PO; SKU or raw attributes on PO lines.
Receive goods via GRN — partial receipts allowed. Rolls auto-barcoded; Unmapped status if SKU cannot be determined at scan time.
Map Unmapped Rolls via bulk staging page: inline SKU assignment or new SKU creation.
Create Purchase Invoice (PI) linked to PO and GRN; GST type auto-determined from supplier state.
Run Landed Cost Allocation: Freight, Duty, Clearing, Misc split by ROLL/METER/VALUE basis; landed_cost_per_roll updated on each roll.
System auto-generates accounting voucher (Dr Inventory + Dr Input GST, Cr Accounts Payable).

Edge Cases
GRN over-receipt (> PO balance): requires admin override with mandatory audit reason.
PI without PO line: allowed with warning; mandatory audit reason; flagged in PO vs GRN vs PI variance report.
Multiple PIs per PO: allowed; PO auto-closes when all lines fully received and invoiced, or force-closed by admin.
Landed cost reallocation after partial dispatch: adjustment posts to Landed Cost Variance ledger; dispatched roll costs are NOT retroactively changed.

Auto Voucher: Purchase Invoice
Dr  Inventory (SKU @ landed cost)      ₹X
Dr  Input CGST / SGST / IGST           ₹Y
Cr  Accounts Payable (Supplier)        ₹X + ₹Y
 | 
6.3 Inventory Management
Roll-level traceability via QR/barcode scan at every stage.
Status lifecycle: Unmapped → Mapped → Allocated → Dispatched → Returned → Mapped/Scrap.
Purchase return sub-status: ReturnedToSupplier (landed cost reversal to variance ledger).
Partial returns: capture measured remaining metres; roll → Returned → inspection → Scrap or re-Mapped with updated length.

Partial Return COGS Rule  ← NEW
partial_COGS = (returned_length_m / original_dispatched_length_m) × landed_cost_per_roll
Credit Note value is calculated on this partial COGS basis, not the full roll cost.
Scrap valuation: at landed_cost_per_roll (full or partial per above); posted to Inventory Write-off expense ledger.
 | 
Dashboard: stock by GSM/Quality/Size, batch aging, unmapped rolls alert, dead stock (> 180 days) flag.

6.4 Pricing & Discounts
All customer rates anchored to the 44" benchmark.
Auto-calculate other widths: derived_rate(W) = base_rate_44 × (W / 44), rounded to nearest ₹1 (configurable).
Customer-specific rate history with validity ranges; special order deal rates recorded in Rate History.
Override at SO/SI requires audit log entry. Override > configured tolerance (e.g. > 5%) triggers approval modal.
Line discount applied before tax. Bill-level discount allocated proportionally by line value for GST correctness; paise handled by largest-remainder rounding.
Discount Allowed (bill-level) posts to Dr Discounts Allowed / Cr AR — distinct from Sales Return Credit Note.
Bulk rate revision: increase or decrease per-metre price across a customer group or product family.

6.5 Sales & Order Management
Standard Flow: SO → DC → SI
SO Draft: enter lines with SKU, qty, rate (auto-derived from 44" benchmark). Click Confirm (Click 1) → credit check; if OK → Confirmed; if blocked → OnHold.
DC: system auto-suggests Mapped rolls. Warehouse staff pick/scan. Enter transporter, vehicle no., LR no. Click Create DC (Click 2).
SI: from DC, click Create SI (one click). Preview shows HSN/GST, discounts, rounding. Post → immutable; auto-voucher generated.

Additional Flows
Direct Invoice (Cash Sales): SO → SI directly; no DC required; full voucher generation still runs.
Proforma Invoice: own series; no accounting impact; Status = Converted when SI is generated from it.
Partial Deliveries: supported; backorders auto-tracked on original SO.
Returns & Replacements: Sales Return workflow creates Credit Note; adjusts inventory and AR ledger.

Auto Voucher: Sales Invoice
Dr  Accounts Receivable (Customer)     ₹X + ₹Z  (net + tax)
Cr  Sales Income                       ₹X
Cr  Output CGST / SGST / IGST         ₹Z
Dr  COGS (landed cost of billed rolls) ₹C
Cr  Inventory                          ₹C
 | 
Edge Cases
Rate override beyond tolerance blocks SO confirmation until manager approves.
Cash sales still go through full voucher generation path.
Partial DC: fulfilled SO lines marked; remaining lines stay open.

6.6 Returns
Sales Return
Create Sales Return against original SI; specify rolls and returned_length_m per roll.
System computes Credit Note value using partial_COGS formula (see Section 6.3).
Post: roll → Returned. Voucher: Dr Sales Return + Dr Output GST; Cr AR.
Inspection: roll moves to Scrap (Dr Inventory Write-off, Cr Inventory) or re-Mapped with new length.
Commission reversal: if trigger was ON_SI_POSTED, reversal entry is automatically created.

Purchase Return
Create Purchase Return against original PI; specify rolls and reason.
Post generates Debit Note: Dr AP; Cr Purchase Return + Cr Input GST.
Roll status → ReturnedToSupplier; landed cost reversal posts to Landed Cost Variance ledger.
PI partially reversed for returned lines; PO remains traceable.

Defective Roll Scrap
Warehouse staff marks roll as Scrap via Roll Inspector or barcode scan.
System posts: Dr Inventory Write-off (at landed_cost_per_roll); Cr Inventory.

6.7 Customer Onboarding & Credit
Capture: name, GSTIN, GST type, state, address, multiple contacts (CustomerContact table), referral source, base rate 44", credit days, credit limit, grace days.
Groups: Cash, Wholesale, Big — multi-value; no group also valid.
WhatsApp number, language preference, and consent flag captured at onboarding (integration Phase 2).
TCS applicable flag captured (computation Phase 2).

Auto-Blocking Logic
Credit Block Rules
Exposure = sum(outstanding AR) + sum(value of Confirmed/PartiallyFulfilled SOs).
OVER_LIMIT:  block if exposure > credit_limit.
OVER_DUE:    block if any invoice overdue by (credit_days + grace_days).
BOTH:        block if either condition is true.
On block: SO → OnHold; internal notification raised.
Admin override: mandatory reason logged to AuditLog.

8. Algorithms & Calculations
8.1 Derived Pricing
Formula
derived_rate(W) = base_rate_44 × (W / 44)
Round to nearest ₹1 (configurable precision).
Override > tolerance (e.g. > 5%) → manager approval required before SO can be confirmed.
Example: base_rate_44 = ₹2,200; width = 36" → derived = 2200 × (36/44) = ₹1,800.
 | 
8.2 Discount Application
Line discount: applied before tax on the specific line item.
Bill discount: allocated proportionally by line value across all lines before tax — ensures correct GST per line.
Rounding: paise handled using the largest-remainder method so that the sum of line totals equals the invoice total exactly.

8.3 Landed Cost Allocation
Formula
allocation_per_roll = total_cost_component × (roll_basis / sum_of_all_roll_basis)
Basis options: ROLL (equal split), METER (proportional to length), VALUE (proportional to base cost).
After allocation: landed_cost_per_roll is updated on the Roll record.
Post-dispatch reallocation: variance posts to Landed Cost Variance ledger; dispatched roll costs are NOT retroactively changed.
 | 
8.4 COGS on Invoice
COGS = sum(landed_cost_per_roll) for all rolls billed in the SI.
Partial return COGS = (returned_length_m / original_dispatched_length_m) × landed_cost_per_roll.
Inventory credit equals COGS debit exactly; no rounding variance on inventory.

8.5 Credit Blocking
Algorithm
1. Compute exposure = sum(outstanding AR) + sum(value of Confirmed/PartiallyFulfilled SOs).
2. Evaluate rule:
     OVER_LIMIT  → block if exposure > credit_limit
     OVER_DUE    → block if any invoice overdue by (credit_days + grace_days)
     BOTH        → block if either condition is true
3. On block: SO → OnHold; internal notification raised.
4. Admin override: reason mandatory; AuditLog entry created.
 | 
8.6 GST Determination
Intra-state supply (customer state = company state): CGST + SGST.
Inter-state supply: IGST.
GST type determined at invoice creation from customer.state vs company.state; manual override with audit log.
HSN code configurable per product category; appears on every invoice line.
Customer gst_type drives invoice format: Composition and Unregistered → Bill of Supply (no tax line).
SEZ customers: zero-rated supply; IGST at 0% with Letter of Undertaking reference.

11.1 Purchases
Create PO with 3 SKUs → partial GRN (2 of 3 SKUs) → verify Unmapped rolls created → bulk-map to SKUs → raise PI → run landed cost by METER basis → verify landed_cost_per_roll updated correctly on all rolls.
Attempt GRN over-receipt without admin override → expect block. Approve as admin → verify audit log entry created.
Raise PI without PO line → confirm warning appears and reason is mandatory.

11.2 Inventory
Scan roll QR → verify full lineage in Roll Inspector (vendor → batch → PI → cost → SO/DC/SI history).
Mark roll as Scrap → verify Inventory Write-off voucher generated at landed_cost_per_roll.
Customer returns 700 m of 1000 m roll → verify Credit Note value = 70% of roll landed cost.

11.3 Pricing & Sales
Create SO for 36" width; verify rate auto-derived from 44" benchmark.
Override rate by > 5% → approval modal appears; approve as manager → SO confirmed.
Confirm SO for credit-blocked customer → SO goes to OnHold; verify exposure calculation includes pending SO value.
Full SO → DC (with transporter and vehicle no.) → SI → verify auto-voucher generated and all ledger balances updated correctly.
Create Proforma Invoice → convert to SI → verify Proforma status = Converted and SI links back to Proforma.

11.4 Returns
Sales return partial roll (700 m of 1000 m) → Credit Note generated with partial_COGS formula → roll to Returned → move to Scrap → verify write-off voucher at partial cost.
Purchase return → Debit Note generated → AP reduced → verify Input GST reversed → roll status = ReturnedToSupplier.

11.5 Accounting
Post PI → verify Dr Inventory + Dr Input GST + Cr AP voucher auto-generated with correct amounts.
Post SI → verify Dr AR + Cr Sales + Cr Output GST + Dr COGS + Cr Inventory voucher generated.
Post receipt payment → allocate to 2 invoices → verify AR aging updated and unallocated balance = zero.
GST Summary for a month → verify Output GST = sum of all SI tax lines; Input GST = sum of all PI tax lines.

11.6 Commission
Set commission ON_SI_POSTED for salesman on customer → post SI → verify commission accrued.
Raise Credit Note against that SI → verify commission reversal entry created automatically with reversal_reason populated.

11.7 Opening Balances
Import opening stock CSV → verify roll records created with correct landed cost and Mapped status.
Import opening AR CSV → verify customer ledger balances match legacy books.
Post opening balance Journal → verify voucher balances (Dr = Cr). Post first live transaction → verify Opening Balance Wizard is locked.


12. Non-Functional Requirements
Area
 | Requirement
 | Notes
 | Performance
 | Dashboard load < 3 s; credit check < 1 s; barcode scan response < 500 ms.
 | Indexes on roll.status, customer.id, si.date.
 | Availability
 | 99.5% uptime during business hours (8 AM – 8 PM IST).
 | Scheduled maintenance outside business hours.
 | Data Integrity
 | Strict double-entry — voucher lines must balance (Dr = Cr) before posting.
 | DB-level constraint + application-level validation.
 | Security
 | Role-based access; sensitive actions require re-authentication; AuditLog is immutable.
 | Passwords hashed; HTTPS enforced.
 | Scalability
 | New product categories and branch locations added without schema changes.
 | Configurable allowed-widths, HSN codes, document series.
 | Data Migration
 | Opening balance wizard with validation and rollback before Go-Live lock.
 | Go-Live lock prevents editing opening balances after first transaction.
 | Backup
 | Daily automated backup; point-in-time recovery up to 30 days.
 | 
 | Audit
 | AuditLog stores before/after JSON for every data change; retention minimum 7 years.
 | Required for GST audit compliance.
